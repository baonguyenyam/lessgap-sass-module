# Database (Prisma ORM 8 + PostgreSQL)

Applies to `prisma/`, `migrations/`, `generated/prisma8/`, `src/lib/db8.ts`,
`src/lib/prisma.ts`, `src/platform/db.ts`, `scripts/backfills/` and any code that
queries. Full standard: `spec/12-migrations-and-data.md`. Reference for the
installed Prisma version: the `prisma-8` skill (`.claude/skills/prisma-8/`);
read its routing table and the reference for the task before writing code.

- **Prisma 8 only.** Never add `@prisma/client`, a `schema.prisma`, a
  `prisma7` dependency, or run `prisma migrate …` / `prisma generate` /
  `prisma db push`: those are Prisma 7 and answer `CLI.COMMAND_MOVED`.
- The schema is the contract, `prisma/contract.prisma`. After editing it:
  `pnpm db:emit`, then `pnpm db:plan --name <owner>_<change>`, review the
  package, fill any `placeholder(...)` with a data transform, self-emit
  (`node migrations/app/<dir>/migration.ts`), then `pnpm db:migrate`. Commit the
  contract, `generated/prisma8/`, the migration package and the snapshot together.
- Before planning, the `db` ref must point at the newest migration's `to` hash
  (`pnpm prisma migration ref set db <hash>`); a plan that says
  `from: (baseline)` over existing migrations is a mistake, stop.
- Never edit `ops.json` or `migration.json`, never edit or delete a merged
  migration, never `--from @empty` except for a deliberate baseline.
- Runtime: `db8` from `@/lib/db8` in new code (`db8.orm.public.<Model>` for
  the ORM, `db8.sql` for the query builder, `db8.raw.sql` only when neither can
  express it, always as a tagged template). `@/lib/prisma` is a frozen
  compatibility layer for existing kit code: do not extend it or import it
  from new code. `tenantDb(ctx)` in module code once it exists (phase 1), and
  the platform client only inside `src/platform/`.
- Every tenant-owned table: `tenantId`, an index starting with `tenantId`,
  per-tenant uniques, RLS declared in the contract, and a classification entry.
  Same change.
- Every migration must work with the code currently deployed. Renames, type
  changes, new required columns and drops go through expand → migrate →
  contract across deploys. Ask before planning anything that could lose data,
  and never answer the planner's data-loss questions (`--delete`) on your own.
- Data fixes on many rows are backfill scripts: idempotent, batched,
  resumable, dry-run by default. Small fixes tied to a schema change are the
  migration's `dataTransform`.
- `src/generated/migrations.ts` is generated by `pnpm build` (prebuild) from
  `migrations/app`. Do not hand-edit it.
- Select only what you use on hot paths and lists; paginate lists. Multiple
  writes that must succeed together go in one transaction.
- Money is `Int` cents; time is UTC plus the tenant's IANA time zone.
- `pnpm db:reset` is the only reset command, and only for development databases.

---

Based on: the `prisma-8` skill shipped with `@prisma/orm-postgres` (contract, migrations, migration model, queries), the expand/contract pattern for zero-downtime schema changes, and PostgreSQL row-level security.
